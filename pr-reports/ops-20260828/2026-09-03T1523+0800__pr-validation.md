## 验证方法与口径

- **基线策略**：工作树钉死在发布 tag，把每个 open PR 的改动 3-way merge 到 tag 上（= tag 代码 + 该 PR 自己的 kernel），逐 PR 隔离验证，归因清晰。
- **构建**：`COMPILER_DIR`/`LINX_SYSROOT` 指向 env_test 工具链，逐目标目录 `bash compile.all`；每 PR 编译前清 `output/`（防陈旧 ELF 污染）。
- **运行**：逐 ELF 跑 `gfrun` + `gfsim`；每个 ELF **裸跑失败再试 4PE，任一通过即 PASS**（`gfrun -s softcore.multiThreadNum=4` / `gfsim --conf fourpe.conf --pto-v02 true`），以规避 4PE kernel 漏配导致的假超时/假断言。
- **判定**：`PASS`=rc0 且无 ASSERTION；`TIMEOUT`=rc124；`FAIL`=其余非零/断言/崩溃；`COMPILE_FAIL`=该目录 compile.all 未产出对应 ELF。
- **职责边界**：只报可用性 + 断言 `file:line`，不诊断根因；仅对「明显与工具版本无关」的失败予以点明（防误归因）。

## 诚实性备注（重要）

1. **#78 QLI 的 COMPILE_FAIL 与工具版本无关**：其 `qli_check_data.s` 用 `.incbin` 写死了绝对路径 `/home/z00947698/superScalar/SuperNPUBench/.../srcsk.bin`，换机器必然找不到。这是 PR 自身的测试数据路径 bug，不应记到"工具版本影响"账上。
2. **本报告已修正一版 4PE 假失败**：首轮仅对路径含 `multi_thread` 的 ELF 加 4PE，导致 `PE4` 命名的 group_norm_grad / gather_v2 被当单 PE 裸跑而假超时；改为「裸+4PE 双跑取更优」后其 gfrun 实为 PASS。上表为修正后结果。
3. **#74 跳过原因**：#74 基于发布 tag 之后的 main（已把 `kernels/` 重构为 single_thread/multi_thread），merge 到扁平的发布 tag 会把整个重构拖入，不再是"tag + kernel"，故无法在发布 tag 基线上忠实验证。如需，可用其自身重构基线单独补验。
4. **gfsim 全 0 通过的背景**：对照同批 env_test 版本追踪的 gfsim 基线通过率约 18%，说明这批在研 PR kernel 恰好都踩到当前时序模型不支持/超时的路径——这是本次要观测的「工具版本对在研 kernel 的影响」信号。
